# Code

Code 是 RepoKit 的代码分析领域：结合仓库上下文、代码事实和项目规则，解释代码的用途、
规模、结构与质量，以及这些性质随改动发生的变化。分析报告提供可定位的证据和缺口；
是否修改代码、阻断交付或发布评审意见，由调用方决定。

## 能力与范围

| 子能力 | 关注的问题 | 当前状态 |
| --- | --- | --- |
| 调用方查询 | 给定声明名在源码中的位置，哪些位置直接调用了它？ | 已实现：`repocli code callers --at <file:line:column>` / Go `FindCallers` |
| 下游调用查询 | 当前声明直接调用了哪些声明？ | `repocli code callees --at <file:line:column>` / Go `FindCallees` |
| 类型层级 | 哪些类型是祖先、后代，关系是继承还是实现？ | `repocli code hierarchy --at <file:line:column>` / Go `TypeHierarchy` |
| [Deadcode](code/dead.md) | 声明是否被使用、是否从声明的入口可达，以及改动前后的用途变化 | 已实现：`repocli code dead` / Go `AnalyzeDeadcode` |
| 规模与复杂度 | 文件和函数长度、类型的方法数量；后续可扩展嵌套与分支复杂度 | 规划方向，尚无对应命令或规则 |
| 耦合与结构 | 依赖范围、循环依赖团、跨模块调用与关系聚合 | 规划方向，尚无对应命令或规则 |
| 架构约束 | 项目声明的模块边界、允许的依赖方向及其违反证据 | 规划方向，尚无对应命令或规则 |

文件、声明、类型、语言模块和工程 Component 是不同的观察粒度。类型成员按语义归属统计，
不能只按同文件或词法嵌套判断；工程 Component 的身份和边界来自 Repository 分析。
子能力按实际需求实现，不为规划方向预建空包或统一规则引擎。

## 从声明查调用方

在仓库中运行 `repocli code callers --at service.go:12:8`，把位置指向函数、方法或构造器的声明名。文件路径相对仓库根，行号和 UTF-8 字节列号从 1 起算。可先用 `rg -n --column` 定位名称。命令读取当前工作树快照，每处静态调用单列调用者、调用位置和 CodeGraph 的置信度。`--json` 额外保留声明、关系证据和分析诊断。

调用关系只按该声明的图身份查询。接口方法可以有指向接口契约的调用边，具体实现只能获得 CodeGraph 实际解析或推断出的入边。空结果表示已分析范围内没有发现对应调用。查询范围遵循 CodeGraph 的分析材料准入规则。函数作为值传给框架时，可以有读取引用而没有直接调用。判断未引用或入口不可达的候选见 `code dead`。

`repocli code callees --at service.go:12:8` 沿相反方向列出一跳调用。每个调用点单独一行，包含调用位置、被调用声明的位置及置信度。同一函数被调用两次会出现两行。嵌套函数体内的调用归属于对应的声明。

## 从类型声明查层级

```sh
repocli code hierarchy --at types.ts:12:7 --direction parents
repocli code hierarchy --at types.ts:12:7 --direction children
repocli code hierarchy --at types.ts:12:7
```

`parents` 递归列出基类及实现的接口，`children` 递归列出派生类型及接口的实现类型。默认 `both` 从选中的类型分别向上和向下展开。要包含兄弟类型，从共同祖先查 `children`。每条关系保留 `extends` 或 `implements`、对端声明及置信度。多继承的共享祖先或循环中的类型再次出现时，保留这条边并标记 `already shown`，每个方向内只展开一次。

`--json` 输出深度优先排列的关系条目，`depth` 从 1 起算，关系保留 CodeGraph 记录的方向和证据。范围取决于快照和静态绑定。Go 接口嵌入可产生 `extends`，struct 嵌入表示组合；基于方法名集合推断的接口实现保留 `heuristic` 置信度。动态基类等未解析关系可结合诊断查看。

## 与底层能力的边界

- **CodeGraph** 提供通用代码事实与查询：声明、成员、命名空间、源码范围、依赖关系及证据。
  它服务 Code 分析，也可以支持 Repository / Component 识别、Diff / Impact 与 View。
  CodeGraph 不归 Code 领域独占，不拥有 RepoKit 的工程 Component、项目阈值或交付策略。
- **Repository / Component 识别** 综合 manifest、构建配置、目录布局和可用的代码组织事实，
  确定工程上下文。Code 分析消费这些结果，不根据目录名称另行发明一套组件归属。
- **Code 子能力** 拥有分析范围、指标或候选规则、项目配置解释、证据呈现和版本比较。
  所需通用语言事实不足时，补足 CodeGraph 或其上游表达；不在 RepoKit 重写语言解析与绑定。
- **Diff / Impact 与 View** 可以复用同一份捕获内容和底层事实，各自拥有影响传播与展示策略。
  共享基础设施不要求这些能力归入 Code，也不允许把裁剪后的局部图当作完整仓库事实。

底层契约见 [CodeGraph](codegraph.md)，工程上下文见 [Repository](repository.md)。

## 分析契约

### 事实、规则与证据

事实描述可观察结果，例如函数占用的源码范围、类型拥有的方法或模块之间的调用边。
规则说明何时值得关注，例如长度阈值、允许的依赖方向。报告应能解释具体值、适用规则、
源码位置及证据；事实和判定不能合并成无法追溯的质量分数。

未来的规模规则需明确计数口径、语言及文件类别，区分普通源码、测试、生成物与依赖材料。
关系分析需声明粒度和关系种类，避免把成员归属边当成调用，或把同一目标的重复调用次数
当成依赖对象数量。大量入边、高密度关系或循环是结构信号，不能单独证明职责或分层错误。
没有项目架构声明时报告观察到的关系；违反分层的结论需要对应的明确约束。

### 范围与完整性

报告保留快照身份、候选范围、实际分析范围与诊断。文件或符号筛选可以只影响返回结果，
不能悄悄删掉判定所需的外部调用者。静态关系不等于运行时执行，弱推断不等于确定调用；
缺失材料、未解析关系或预算耗尽时，没有发现问题不能表述为已经证明代码健康。
具体范围和完整性要求由各子能力声明，见 [Deadcode](code/dead.md)。

### 版本比较

比较的两侧各自使用同一快照的源码、位置和关系，保留匹配缺口；不拼接不同版本的证据链。
子能力按自己的语义区分历史状态与本次变化，支持解释新增、改善或恶化。
Deadcode 已实现候选身份匹配和用途变化分类，具体字段与限制由其文档维护；
其他能力实现时复用快照和比较原语，不提前统一尚未出现的报告模型。

## 文件组织与实现

```text
docs/
├── code.md                  # Code 领域定位、公共约束与能力索引
├── code/
│   └── dead.md          # deadcode 使用方式、规则、结果与实现边界
└── codegraph.md             # 多个上层能力共享的代码事实与仓库适配

toolkit/go/
├── callers.go / deadcode.go # FindCallers、AnalyzeDeadcode 与公共类型
└── internal/
    ├── code/
    │   ├── navigation/  # 声明定位、下游调用与类型层级
    │   ├── callers/     # 声明位置与直接调用证据
    │   └── dead/        # deadcode 流程、规则、比较与所属测试
    ├── analysis/            # 共享捕获、构图与分析原语
    └── codegraph/           # 共享 CodeGraph 的仓库适配与查询
```

各 Code 子能力复用 analysis 的快照与共享代码事实，CLI 展示位于 `apps/cli/internal/cli/code/`。
公共命令与 SDK 入口按实际使用需求演进，目录归属本身不要求新增一层转发 API。

各子能力的行为契约和 case 随实现维护；目录迁移保留现有 spec/case 及验证场景。
